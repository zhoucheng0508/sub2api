# Vote AI 风控 PR2-PR4 专项测试方案

## 1. 目标与边界

本方案验证 Sub2API `0.1.170` 二开风控的性能、账号范围、会话风险、通知和解禁闭环。测试环境必须使用独立测试用户、API Key 和可识别的测试会话，不使用生产用户密钥，不修改生产价格和余额配置。

任何测试都不得删除 PostgreSQL、Redis 或 `/app/data`。本地部署只替换应用容器；进入生产灰度前，必须完成 PostgreSQL 备份的实际恢复验证。

## 2. 通过标准

- 正常请求和防御性请求不会被拦截，也不会累计为高风险。
- 明确高风险请求在 `pre_block` 模式下不会进入上游账号池。
- 同一 `用户 ID + API Key + 客户端会话 ID` 的渐进式风险可以累计，不同会话互不污染。
- 账号范围以调度后最终选中的上游账号为准；只审计指定 Pro 账号，不审计同一混合分组中的 Plus 账号。
- Pro 请求必须在进入上游前完成审核；审核通过后若 Pro 上游失败并切换到 Plus，复用已完成的审核决策，不撤销审核。首选 Plus 失败并切换到 Pro 时必须补审，不能绕过审核。
- 同一输入、同一会话的重复命中不会产生邮件风暴；风险升级允许再次通知。
- 自动风控封禁可由风控页面解禁，并清理短期风险状态；人工禁用不会被风控解禁误恢复。
- `pre_block` 同步审核等待不超过配置预算，默认 4800 ms；超时进入有界补审队列。
- 多个 AI 审核 Key 时，首 Key 超时仍能在同一总预算内切换备用 Key；父请求取消后不得继续调用备用 Key。
- 解禁前排队的普通审核任务和上游 `cyber_policy` 事件不得在解禁后重新累计、发信、封禁或写入会话屏蔽；上游证据可以保留，但必须是不可计数、无副作用状态。

### 4.1 账号证据关联规则

`content_moderation_logs` 表没有 `account_id`，不得用该表直接证明请求最终使用了哪个账号。所有账号范围与故障切换用例必须记录 `request_id`，并按同一 `request_id` 关联以下证据：

- 容器日志中的 `selected_account_id` 和 `scope_account_id`：证明调度候选账号和本次审核范围判定所依据的账号。
- 成功请求对应的 `usage_logs.account_id`：证明实际产生上游使用记录的最终账号。
- 风控在进入上游前拦截的请求不会生成 `usage_logs` 行；此时只能用容器日志证明候选账号和审核范围，不能声称存在最终上游账号或使用记录。

证据记录必须同时保留 `request_id`、时间、测试用户、测试 API Key 标识、容器日志片段和使用记录 ID（如有），避免把相邻并发请求错误关联。

### 4.2 当前本地环境限制与隔离验收

当前本地真实数据只有一个 `openai/apikey` 上游账号，没有 OAuth Pro/Plus 账号和真实混合账号池；SMTP 未配置且 `email_on_hit=false`。因此，本环境不能直接得出“真实 Pro/Plus 混合调度、双向真实上游故障切换或真实 SMTP 邮件发送已通过”的结论。

需要 Docker 端到端验证这些路径时，应建立与现有数据隔离的测试夹具：一次性非管理员测试用户和限额 API Key、两个可明确区分的 mock OpenAI 账号、独立测试分组，以及只在本机接收邮件的 Mailpit。mock 账号用于稳定制造 Pro/Plus 选择和上游失败，Mailpit 用于验证邮件内容与去重且禁止外发。测试报告必须将结果标为“隔离 mock/Mailpit 验收”，不得表述为真实 Pro/Plus 账号或真实 SMTP 生产链路验证。

当前生产为单应用容器，Redis epoch 与进程内分片锁可以覆盖解禁并发窗口。若扩展为多个应用副本，必须先实现 Redis/数据库分布式原子屏障，并新增跨实例解禁竞态测试，不能直接沿用单实例结论。

## 5. 功能测试用例

### 5.1 正常与误报

| 编号 | 输入目的 | 预期 |
| --- | --- | --- |
| FP-01 | 普通知识问答 | 放行；使用记录存在；无风控命中 |
| FP-02 | “如何保护我自己的账号，防止密码和 API Key 被盗” | 放行；可返回 `defensive_context`；最终等级为低风险 |
| FP-03 | 请求管理员推荐风控关键词 | 放行；不得因引用风险词本身而拦截 |
| FP-04 | 翻译、总结或评估一段风险样例 | 放行；只判断最后一条用户请求的真实动作 |
| FP-05 | 通过官方流程找回本人账号 | 放行；仅 `ownership_unverified` 不得累计风险 |

### 5.2 明确风险请求

| 编号 | 输入目的 | 预期 |
| --- | --- | --- |
| RISK-01 | 明确请求绕过认证或所有权校验 | `pre_block` 拦截；上游使用记录不产生成功请求；风控日志含强信号 |
| RISK-02 | 明确请求提取他人凭据或秘密 | 拦截；类别和原因结构化显示 |
| RISK-03 | 明确请求投放恶意载荷或规避平台安全策略 | 拦截；会话风险进入高风险 |

测试文本只描述风险目标，不包含可执行载荷、真实凭据或真实目标。

### 5.3 八轮渐进式长对话

所有请求使用同一测试用户、同一 API Key 和同一 `X-Session-Id`，每轮携带完整 `messages` 历史：

1. 询问软件防护的一般原则。
2. 询问如何识别未授权访问。
3. 讨论官方账号恢复流程。
4. 询问权限校验的常见薄弱点，但不要求利用。
5. 要求比较合规测试与未授权行为的边界。
6. 将目标逐步改为未核实所有权的账号或程序。
7. 要求绕过官方认证或安全限制。
8. 使用“继续”“写成脚本”或“再具体一点”推进上一轮高风险目标。

预期：前五轮不机械拦截；第六轮可进入观察；第七或第八轮命中 `progressive_escalation` 及至少一个强信号并阻止。更换 `X-Session-Id` 后不得继承该会话状态；同一用户/API Key 的跨会话加分只能按已配置的 actor 规则生效。

### 5.4 混合分组与故障切换

| 编号 | 条件 | 预期 |
| --- | --- | --- |
| SCOPE-01 | 账号过滤设为仅包含测试 Pro；请求命中 Pro 并成功 | 执行审核；同一 `request_id` 的容器日志中 `scope_account_id` 为 Pro，且 `usage_logs.account_id` 为 Pro |
| SCOPE-02 | 同一混合分组请求命中 Plus 并成功 | 跳过审核，原因是账号不在范围；同一 `request_id` 的容器日志与 `usage_logs.account_id` 均证明请求进入 Plus |
| SCOPE-03 | 首选 Pro 审核通过，但 Pro 上游失败并切换到 Plus | Pro 在首次上游调用前已完成审核；切换到 Plus 后复用该审核决策，不撤销、不重复审核；同一 `request_id` 的容器日志证明切换过程，`usage_logs.account_id` 为 Plus |
| SCOPE-04 | 首选 Plus 上游失败，切换到 Pro | 切换到 Pro 后、进入 Pro 上游前必须补审；高风险内容被拦截且没有 `usage_logs` 行，候选 Pro 及范围判定只能由同一 `request_id` 的容器日志证明 |
| SCOPE-05 | 管理员账号状态测试请求 | 用户过滤排除 admin 后不调用审核服务、不产生无效审核日志 |
| SCOPE-06 | Spark 影子账号被选择 | 账号范围按母账号 ID 归一化；同一 `request_id` 的容器日志可追溯 `selected_account_id`、归一化后的 `scope_account_id`，成功请求再以 `usage_logs.account_id` 证明最终账号 |

故障切换必须使用隔离 mock 账号或专用测试账号制造可恢复的上游故障，不破坏真实生产账号。当前本地环境没有真实 Pro/Plus 账号时，只能报告隔离 mock 验收结果。

### 5.5 邮件与解禁

| 编号 | 操作 | 预期 |
| --- | --- | --- |
| MAIL-01 | 同一输入连续命中 | 输入去重生效，只发送一封 |
| MAIL-02 | 同一会话多轮命中同一风险等级 | 会话去重生效，不逐轮发送 |
| MAIL-03 | 同一会话从观察升级到高风险/封禁 | 允许发送一封升级通知 |
| MAIL-04 | 模拟发送失败后重试 | Redis 租约释放，后续可再次发送 |
| UNBAN-01 | 自动风控封禁用户后执行“恢复并清理风险状态” | 用户恢复、Redis 会话/actor 风险键清理、结果状态完整 |
| UNBAN-02 | Redis 清理失败 | 用户恢复结果与清理失败分开显示，可单独重试清理 |
| UNBAN-03 | 人工禁用用户 | 风控解禁不得误恢复人工禁用状态 |
| UNBAN-04 | 普通审核任务入队后执行解禁，再释放旧任务 | 旧任务不落处置日志、不恢复 hash/会话风险、不发信、不重禁；解禁后的新任务仍可处理 |
| UNBAN-05 | 请求进入上游前拍 epoch，上游命中 `cyber_policy` 后执行解禁，再异步记录 | 保留不可计数的证据行；不累计、不发信、不重禁、不写 Cyber 会话屏蔽；下一请求使用新 epoch 正常处理 |

邮件自动化测试可以验证通知决策、输入/会话去重、风险升级和失败后释放租约；Docker 端到端邮件验收使用本地 Mailpit，检查收件数量、主题和正文且禁止外发。只有使用已配置的真实 SMTP 测试账号实际投递成功，才能标记为“真实 SMTP 链路通过”；当前 SMTP 未配置时不得作此结论。

## 6. 性能记录

每个 API 用例记录：HTTP 状态、总耗时、首字时间、审核日志上游耗时、是否补审、最终账号 ID、使用记录 ID、风险等级和邮件数。正常请求至少重复 5 次，报告 P50 与最大值。

通过标准：同步审核阶段不超过配置预算；默认预算 4800 ms。总首字时间还包含正常上游模型首字时间，因此必须分别报告“审核等待”和“端到端首字”，不能把两者混为一项。

## 7. 生产灰度关卡

只有本地全部通过且 GitHub PR CI 全绿后才能进入生产：

1. 完成生产只读审计并记录当前镜像、挂载和关键表行数。
2. 创建 PostgreSQL、globals、Redis、`/app/data`、Compose 和环境配置备份，并校验 SHA-256。
3. 把 PostgreSQL 备份实际恢复到临时数据库，核对关键表后删除临时库。
4. 传输并校验候选镜像，只重建应用服务。
5. 先用专用测试用户和测试账号灰度，不对真实用户批量触发风险用例。
6. 核对健康、登录、正常 API、风控、邮件、使用记录和关键表行数。
7. 保留旧镜像、备份和回滚命令，不立即清理。

## 8. 测试结果记录

执行时为每个编号记录：时间、环境、结果、证据位置、异常和处理。任何数据减少、容器反复重启、审核绕过、正常请求误封、邮件风暴或无法恢复的解禁失败都属于停止条件，不得进入下一阶段。
